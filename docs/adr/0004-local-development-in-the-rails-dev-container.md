# 4. Local development in the Rails dev container

- **Status:** Proposed
- **Date:** 2026-09-16
- **Deciders:** Tim Gladwell

## Context

timbot needs a local development environment that runs the same Postgres major
as CI and the cluster (ADR 0001), and that can be wiped and rebuilt in seconds.

Local development cannot reproduce production: the cluster is arm64 on a Pi 4
under shared memory pressure, and the dev machine is not. Local parity is
therefore about avoiding integration surprises in the toolchain, Ruby, system
libraries and database. Production workload behaviour is out of reach.

Rails 8 ships a dev container generator (`bin/rails devcontainer`), and the
Rails guides present it as a supported way to develop. It provides the database
lifecycle, a debugger-ready container and VS Code integration.

## Decision

### Use the Rails-generated dev container

Local development runs in `.devcontainer/`, generated by `bin/rails devcontainer`.
The app runs in the Rails dev container image, and PostgreSQL runs as a sibling
Compose service. `bin/setup` runs when the container is created.

### Vanilla Rails wherever possible

Development uses the standard Rails process with no wrapper tooling:
generators, `bin/setup`, `bin/dev`, `bin/rails test`, `bin/jobs`, and the Rails
guides as the reference. The editor integration is what the dev container and
Ruby LSP provide.

Generated files are kept close to what the generator writes. Deviations are
allowed only when an existing decision requires them, and each one is listed
here. Regenerating on a Rails upgrade is then a diff against this list.

| Deviation from generated files | Required by |
| --- | --- |
| Redis/Valkey service and `REDIS_URL` removed | ADR 0001: Solid Queue on Postgres, no Redis |
| Production `database.yml` kept as a single database; only the generator's `DB_HOST` block is taken | ADR 0001: single logical database |
| `postgres` image pinned to the same tag as CI (`postgres:18.6-trixie`), volume at `/var/lib/postgresql` | ADR 0001 version pin; Postgres 18 images moved the data directory |
| `postgres-client` feature version set to the pinned major | The feature's default lags the current major |
| Ruby LSP added under `customizations.vscode` | Test explorer and debugger in the container |

### Container runtime is not part of the decision

Any Docker-compatible engine works. Rails does not manage the engine; the Rails
guide says only to install Docker. `docs/development.md` records what the
current machine uses.

## Consequences

### Positive

- Ruby, system libraries and the Postgres client match the Debian-based
  production image more closely than a macOS host install.
- The database lifecycle is disposable. Removing the Compose volume and
  rebuilding recreates everything through `bin/setup`.
- Setup is one step for any machine with a container runtime and VS Code.
- Staying on generated files keeps Rails upgrades and guides directly
  applicable.

### Negative / risks

- **Tooling outside the container still needs host Ruby.** Claude Code runs on
  the host, and its Ruby LSP plugin runs `ruby-lsp` from the host's `PATH`. That
  means the pinned Ruby and the bundle are installed on the host too, only for
  code intelligence. Running Claude Code inside the dev container would remove
  this, at the cost of authentication and configuration inside the container.
- **Not the production image.** The dev container is a development image, not
  the `Dockerfile` that ships. Integration failures in the production image
  (assets, boot in production mode, `DATABASE_URL`) are caught by CI booting the
  built image (#3), not locally.
- **Architecture differs.** The dev machine is amd64 and the cluster is arm64.
  Architecture-specific failures surface in CI on arm64 runners (#3) or on the
  cluster.
- **A container runtime is a prerequisite**, and on macOS it runs a Linux VM
  with its own memory reservation.

## Alternatives considered

| Option | Rejected because |
| --- | --- |
| Postgres installed on the host (Postgres.app, Homebrew) | No disposable lifecycle. The version pin depends on what is installed on each machine. Tried first and removed |
| Postgres in a container, Rails on the host | Keeps host tooling, but loses the Linux toolchain parity and the debugger and editor integration the dev container provides |
| k3s locally (for example, Colima with Kubernetes) to reuse the deploy manifests | Much more to run and learn for development work. Local development cannot reproduce the cluster's workload anyway |
| Production image run locally as the development environment | Built for deploying, not iterating: no bind-mounted code, no debugger, slow rebuilds |
